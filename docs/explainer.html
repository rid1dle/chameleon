    Chapter 3

    The TLS ClientHello

    The first thing a client says in HTTPS is the ClientHello: "here are the encryption methods I support, the extensions I understand, the key-exchange groups I can do, and the protocols I want next (ALPN, for example h2)." The server picks from these lists. The lists themselves, in their exact order, are what identify the client. Chrome, Firefox, curl and Java each ship a different TLS library, so each sends different lists.

    GREASE: deliberate noise

    Chrome inserts fake values into its lists on purpose, called GREASE (RFC 8701). They keep servers from breaking when new values appear. Every GREASE value has the same shape: two equal bytes, each ending in a, such as 0x0a0a, 0x1a1a ... 0xfafa. Chrome picks a different one each connection, so any comparison must treat every GREASE value as the same thing. cfprobe's fingerprint code turns them all into the word GREASE for exactly this reason.

    Reading a JA4

    A JA4 has three parts joined by _. Part a is readable. Parts b and c are the first 12 hex characters of a SHA-256 hash.

    t13d1517h2_8daaf6152771_cb7bf5808d99
    PieceHereMeaning

    version13highest TLS version offered: 1.3

    Chapter 4

    The HTTP/2 fingerprint

    After TLS, an HTTP/2 client opens with a connection preface: a SETTINGS frame (its preferences), usually a WINDOW_UPDATE (how much data it lets the server send), then a HEADERS frame for the first request. The spec leaves all of these choices to the client, so each HTTP/2 library chooses differently. Akamai's 2017 format writes them as one string with four |-separated fields.

    SETTINGS IDs

    IDNameChrome 152Firefox 155 (fork profile)curlOkHttpcfprobe
    1HEADER_TABLE_SIZE6553665536
    2ENABLE_PUSH0000
    3MAX_CONCURRENT_STREAMS100
    4INITIAL_WINDOW_SIZE629145613107265536167772162097152
    5MAX_FRAME_SIZE1638416384
    6MAX_HEADER_LIST_SIZE26214416384

    An empty cell means the client did not send that setting. Note curl sends 3, 4, 2: not in ascending order. Order is part of the fingerprint.

    Chapter 5

    The three tools studied

    The repo reads three open-source projects at pinned commits. Together they form a common pipeline: a program that cannot pass a challenge asks a real browser to pass it, takes the reward (a cookie), and reuses it from its own, non-browser network stack.

    Suwayomi-Server

    Self-hosted manga server (Kotlin, JVM). All its extensions share one OkHttp client. Its CloudflareInterceptor spots a challenge (403/503 plus Server: cloudflare), asks FlareSolverr to solve it, then replays the original request from OkHttp with the browser's cookies and User-Agent.

    FlareSolverr 3.5.2

    A proxy in Python. You POST a URL to /v1; it opens it in a real Chromium 152 (new headless mode, driven by a modified undetected-chromedriver), waits out or clicks through the challenge, and returns the cookie jar plus the exact User-Agent.

    curl-impersonate (lexiforest fork)

    A patched curl on BoringSSL with 48 browser profiles. It copies TLS, HTTP/2 and header order. It runs no JavaScript, so it cannot pass a challenge; its role is the replay client with a matching fingerprint.

    The survey (other-projects.md)

    Twelve more projects in four classes by which layer they fake: A patched automation browsers, B engine forks (camoufox), C wire impersonators (curl_cffi, tls-client, uTLS), D solver services (FlareSolverr, Byparr).

    Chapter 9

    The cfprobe engine

    Until now every measurement used other people's tools. engine/ is a Rust program, cfprobe, that makes the requests itself and reports what happened. It has its own connection stack: Cloudflare's BoringSSL bindings (boring 5.6.0) for TLS and hyper 1.13 for HTTP/1.1 and HTTP/2. It has no browser profiles and does not solve challenges; its TLS and HTTP/2 settings exist to change one variable at a time in an experiment.

    Three kinds of value

    Every value in a cfprobe report belongs to exactly one kind, and the report keeps them apart:

    Configured

    configured_tls, configured_h2: what we asked for. None means "library default", never a guess at what the default is.

    Measured by the client

    tls: read from BoringSSL after the handshake (version, cipher, ALPN, session reuse, client random, certificate chain). Plus status, headers, timings.

    Measured by a receiver

    fingerprint: what TrackMe or the Worker saw: JA4, HTTP/2 frames, header order. The only honest source for wire fingerprints.

    How we know both sides saw one handshake

    The 32-byte ClientHello random is chosen by the client and seen by the receiver. cfprobe compares them: same_handshake_as_client: true on both TrackMe and the Worker.

    // engine/src/tls/mod.rs: the client-side view, read after the handshake
pub(crate) fn observe(ssl: &SslRef) -> TlsObservation {
    let mut random = [0u8; 32];
    let n = ssl.client_random(&mut random);
    TlsObservation {
        version: ssl.version_str().to_string(),          // "TLSv1.3"
        cipher: ssl.current_cipher().map(...),            // TLS_AES_128_GCM_SHA256
        alpn: ssl.selected_alpn_protocol().map(...),      // "h2"
        session_reused: ssl.session_reused(),
        client_random: hex(&random[..n]),                 // matched against the receiver
        ...
    }
}

    Chapter 10

    Reading Cloudflare's answer

    Phase 2 started from a bug report: a detector called three normal pages "challenges". Before fixing it, the pages were fetched again, once each, and the strings counted. All three hits were the same line:

    var u='/cdn-cgi/challenge-platform/scripts/jsd/main.js?ray=...'

    That is Cloudflare JavaScript Detections: a background script that scores the visit for later requests. It does not block the page it sits on. A real challenge page loads a different script from the same folder (/h/b/orchestrate/), defines window._cf_chl_opt, and comes with the header cf-mitigated: challenge. The old rule matched the folder name, so it matched both.

    PageStatuscf-mitigatedchallenge-platform_cf_chl_optReally
    asurascans.com, bookmyshow, discord.com200absent1 (jsd script)0normal page
    www.cloudflare.com200absent00normal page ("Turnstile" in its menu)
    zone /c/echo403challenge17real Managed Challenge
    The fix (D17)No single string decides a verdict any more. Markers are structural: a header, a script URL, a page-defining object, a class attribute. cf-mitigated: challenge plus a challenge page in the body is a confirmed challenge (high). The page markers without the header give only CHALLENGE_INDICATOR, at medium or low confidence. A 200 is a normal page, never "bypassed".

    Ten verdicts

    Every response, and every request that got no response, gets exactly one:

    NORMAL_PAGEREDIRECTCHALLENGE_INDICATORCONFIRMED_CHALLENGE_RESPONSERATE_LIMITEDACCESS_DENIEDORIGIN_UNAVAILABLETLS_FAILURECONNECTION_FAILUREUNKNOWN

    Error numbers in a body (error code: 1015) count only when the response came through Cloudflare (cf-ray or server: cloudflare): an origin that prints that text is not Cloudflare's rate limiter.     Four things Cloudflare was measured doing

    Retry-After counts down to 0 while still limiting

    The rate limiter sent Retry-After: 0 on a 429. Honouring it literally made three requests within 12 ms (D23). Now a 0 is floored at the normal backoff and a long value is capped.

    The clearance is bound to the User-Agent, again

    FlareSolverr solved /c/echo; cfprobe replayed the cookie. Solver's UA: 200, on HTTP/2 and on HTTP/1.1. cfprobe's own UA: 403. A third client stack reproduces E1.

    A body cut mid-stream arrives complete

    The Worker sent 1000 bytes, then errored. cfprobe and curl both got 200 with 1000 bytes and no error. Behind Cloudflare, no client can see that the origin died.

    Brief 522s on a new Custom Domain

    Four requests in the first two minutes got 522; a rerun minutes later had none. Likely propagation to edge servers (an inference, not confirmed by Cloudflare).

    Performance, profiled

    Loopback, release builds, 32 concurrent requests over TLS HTTP/1.1. The first benchmark had cfprobe behind reqwest. A sampling profile found the cause: an async tokio::sync::Mutex around the connection pool, taken twice per request, so each contended lock parked and woke through the scheduler. It is never held across an await, so a plain std::sync::Mutex is correct.

    Medians of 5 alternating runs, 100,000 requests each. Memory stayed flat across 1,000,000 requests on both protocols (15.1 MB and 17.7 MB peak). 10,000 fuzzed responses over 20 seeds: 0 failures, no panics.

    Chapter 11

    Proxy routing and Tor

    cfprobe can send every connection through a proxy: --proxy URL, the CFPROBE_PROXY variable, or a config entry. HTTP CONNECT, HTTPS (TLS to the proxy, then CONNECT) and SOCKS5 are supported. The rule has three cases, and the second one is the point:

    SituationWhat happens
    No proxy definedDirect connections, as before proxies existed, and the run says so: cfprobe: no proxy defined: running in no-proxy mode (direct connections). Each record carries "route": {"kind": "direct"}
    A proxy definedEvery connection goes through it. If it fails, the request fails with the stage (unreachable, TLS, auth, refused tunnel). There is no direct path in this mode, so nothing can fall back to one
    A proxy defined but invalidA configuration error. It never turns into direct mode

    One function, networking::dial, opens every connection, and a test scans the source and fails if anything else calls TcpStream::connect or lookup_host. With a proxy, the destination name goes to the proxy and is never looked up locally; socks5:// is treated as socks5h:// for that reason (curl does the opposite). Credentials never reach logs or records.

    Tor, in one flag

    # start a local Tor SOCKS proxy (Docker, pinned image) and wait for it to bootstrap
scripts/tor.sh up
# one command through Tor
cfprobe --tor proxy-check https://lab.riddlelab.dev/echo
# or every tool in this shell: cfprobe, zone scripts, FlareSolverr solves
eval "$(scripts/tor.sh env)"

    --tor is shorthand for --proxy socks5h://127.0.0.1:9150, with the same rule: if Tor is down, the request fails. There is deliberately no "new identity" command: changing exits to get past a block would be circumvention. Tor also settled an open question: through it, the destination saw a different client address than direct, and proxy-check --expect-egress-ip fails on a mismatch, so the routing is proven, not assumed.

    Chapter 12

    Rules that keep it honest

    A 200 is "reached", never "bypassed"

    A 200 can mean the cookie worked or that the rule never matched. Only Cloudflare's event managed_challenge_bypassed says which.

    The receiver outranks the client

    E2's first write-up trusted FlareSolverr's log. Cloudflare's event log showed an interactive solve. The correction is kept in the file (E2-1a).

    Not captured is not zero

    A field a receiver does not record prints as not captured; a skipped step is absent, not 0 ms.

    Nothing private leaves the machine

    Cookie values become their length; client IP, location and ISP become <removed>. Six captures were scrubbed before this repo went public. scrub.py --check now runs before every commit and caught real leaks (D25).

    No silent fallback

    A defined proxy that fails stops the request; it never quietly goes direct. No proxy at all is a stated mode, printed on every run.

    Reproduce before fixing

    The false positive was fetched again and counted before any rule changed. Every one of the 28 defects has a test that failed before its fix.

    Glossary

    ALPN
    Application-Layer Protocol Negotiation. A TLS extension where the client lists the protocols it wants next (h2, http/1.1) and the server picks one.
    ClientHello random
    32 random bytes the client puts in its ClientHello. Both ends see the same value, so it identifies one handshake. cfprobe uses it to prove the receiver saw the same connection.
    GREASE
    Reserved fake values (RFC 8701) clients insert so servers tolerate unknown values. Shape: two equal bytes ending in a.
    JA3, JA4, peetprint
    Summaries of a ClientHello. JA3 keeps extension order and drops GREASE. JA4 sorts extensions and drops GREASE. peetprint sorts and keeps GREASE.
    Akamai HTTP/2 fingerprint
    SETTINGS|WINDOW_UPDATE|PRIORITY|pseudo-header order, from the first frames of an HTTP/2 connection.
    Managed Challenge
    A Cloudflare challenge that runs silent browser checks and shows a checkbox only when those are not convincing.
    cf_clearance
    The cookie Cloudflare sets after a passed challenge. Valid for the zone's Challenge Passage time (default 30 minutes). On this Free zone, tied to the User-Agent but not to the TLS fingerprint (E1).
    request.cf
    The object a Cloudflare Worker receives with Cloudflare's metadata about the request: TLS version, cipher, header names, location (scrubbed in this repo) and, on Enterprise, bot fields.
    TrackMe
    An open-source fingerprint echo server (the code behind tls.peet.ws), run locally in the lab.
